Everything you (n)ever wanted to know about dates!

Different programming languages handle date/time values quite differently. This page aims to compare different implementations, representations and formats to help you decide how you want to handle date/times in your code, and how to avoid common mistakes.

There are four main ways of representing a timestamp:

UTC Timestamp

A UTC timestamp stores a unique point in time. It is usually represented as a number of seconds since an epoch, such as the Unix epoch (midnight at the beginning of 1 January 1970, UTC). UTC timestamps always represent time as UTC, and thus do not embed any time zone information, though they can always be converted to any time zone (e.g. when displaying to a user).

This is generally the preferred format for timestamps. Unless you have a compelling need for a different format you should almost always use UTC timestamps.

When serializing, the recommended format is RFC 3339 / ISO 8601. UTC timestamps always have a “Z” suffix to indicate that the timestamp is in UTC, but that we aren't storing any specific UTC offset.

The current UTC timestamp is , equal to seconds since the Unix epoch.

Zoned Date/Time

As the name implies, a zoned date/time represents a date and time with a time zone. It is a combination of a UTC timestamp and a time zone.

Zoned date/times function as a bridge between an exact timestamp and a wall-clock time. They can simultaneously represent an instant in history (like a UTC timestamp), and a local, wall-clock time (like a plain date/time). The stored time zone makes it easy to convert between the two forms. Zoned date/times are the preferred format if a time zone is required.

Note that a time zone (e.g. ) is different from a UTC offset (e.g. ). A single time zone can change its offset at any point, such as during daylight saving transitions. Zoned date/times always store a named time zone, not an offset. Colloquially some people refer to daylight saving and standard time as being two separate time zones, but this is not true.

Zoned date/times are the only values that can safely be used for date/time arithmetic: adding or subtracting durations can be done correctly. Because of daylight saving and other time zone offset transitions, you cannot assume that any given day is 24 hours long, and sometimes even an entire day can be skipped from a local calendar, so e.g. adding 24 hours to a timestamp may not be equal to the same time on the next day. No other date/time format can correctly account for this.

Zoned date/time values are serialized using RFC 9557, which extends the venerable RFC 3339 / ISO 8601 format by storing the time zone in square brackets after the offset.

The current zoned date/time is .

Plain Date/Time

A plain date/time value represents a time zone-unaware time point. Rather than storing time in UTC, we instead store it in an implicit time zone; this is usually local time.

Using this format is generally not recommended. Because we are not storing a time zone, these values cannot be safely stored or sent over a network. They also cannot be safely parsed or converted to another time zone due to ambiguities around daylight saving transitions.

When using plain date/time values, you will need to be very careful to always interpret them in the same time zone, particularly when serializing or transmitting date/time values. It is almost always better to instead use UTC timestamps (if the time zone is not important), or zoned timestamps (if the local time zone is required). Parsing a plain date/time is dangerous because most platforms will assume that the timestamp is in local time, which is often not true. Converting a plain date/time to any other format is potentially ambiguous, since e.g. time may be skipped or repeated when daylight saving starts or ends.

Formatted plain date/time values do not have any “Z” suffix or other time zone information.

The current plain date/time is (assuming we are using the local time zone).

Offset Date/Time

An offset date/time value represents a UTC timestamp and a time zone offset. An offset represents the difference from UTC in hours/minutes, but does not store the specific named time zone. For example, we would store the current offset of “” rather than the current time zone “”.

This format is also not recommended. While offset date/time values can be safely converted to either UTC or to a local date/time value, it is not possible to perform any arithmetic on these values. An offset date time cannot account for any time zone transitions. For example, adding/subtracting days, weeks or months from an offset date/time is not possible: any such calculations will return incorrect results due to daylight saving or other time zone offset transitions. Thus it is almost always preferred to use a zoned date/time value rather than an offset-based one.

Parsing

Parsing timestamps can be quite dangerous due to different kinds of ambiguities and assumptions. This section discusses common issues when parsing different formats.

UTC timestamp formats

RFC 3339 with Z

Parsing a UTC timestamp with a trailing Z, such as is generally safe. Almost all programming languages can parse this format without any issues or ambiguities.

Epoch Time

Epoch times like are generally safe to parse, though it is good to pay close attention to the specific epoch and unit:

  • : seconds since the Unix epoch
  • : milliseconds since the Unix epoch
  • : microseconds since the Unix epoch
  • : nanoseconds since the Unix epoch
  • : seconds since 1 January 2001 (sometimes used on macOS)
  • : 100-nanosecond intervals since 1 January 0001 (sometimes used on Windows)
You'll also want to ensure your code is not affected by potential overflows, such as the Year 2038 problem caused by Unix Time reaching a value of 231 (approx. 2.1 billion) seconds in 2038.

    Nonetheless, this explicit offset + time zone format can have offset ambiguities, which are unavoidable in the real world. An offset ambiguity occurs if the time zone definition has changed since the timestamp was originally serialized, in which case you may find that the embedded offset ( in this example) no longer matches the specified time zone.

    For example, suppose you create a reminder in 2018 for 2019-12-23T12:00:00-02:00[America/Sao_Paulo], which is a daylight saving time in Brazil. Before that time comes, Brazil abolished daylight saving in early 2019, so the real UTC offset becomes -03:00. Should your reminder still fire at noon (keeping the local time), or should it fire at 11:00 AM (keeping the exact time)?

    How to resolve offset ambiguities is always a case-by-case decision, so it's not really possible to give a general answer here. The JavaScript Temporal API will throw an exception by default, but allows you to choose to prefer either UTC or the local time. Resolving in favour of the local time can lead to a further transition ambiguity though, so that will need to be accounted for too.

    While having to handle offset ambiguities may seem annoying, they are inherent to how time zones are defined in the world. No other timestamp format (other than RFC 9557 with explicit offset + time zone) can even detect offset ambiguities, and will instead silently choose one or another resolution, which can lead to further bugs.

Plain Date/Time

Parsing a plain date/time with no time zone information, such as is dangerous. Many programming languages will automatically attempt to parse the value as if it was local time, even if it is intended to be in a different time zone.

For example, parsing a plain date/time using new Date("") in JavaScript will always parse it in the browser's local time zone. If the value is instead intended to be in UTC or another time zone, the result will be incorrect. You would have to append a “Z” manually before parsing, or use a dedicated plain date/time type like Temporal.PlainDateTime.

Even if you are intending to parse the value in the local time zone, you will still have problems around daylight saving or other time zone transitions. During daylight saving transitions, timestamps in local time may be skipped or repeated. Attempting to parse a timestamp during a transition to or from daylight saving is not possible without specifying a manual disambiguation. For this reason, local date/time values should almost always be avoided in favor of UTC or zoned timestamps.

Even creating and immediately parsing a local date/time value is not safe: new Date(Temporal.Now.plainDateTimeISO().toString()) will return an incorrect current date during a transition, even though we are immediately parsing the value we just created. Because code like that will “mostly” work, but suddenly break once or twice a year, it can be very hard to debug and should be avoided entirely by simply using UTC timestamps. If we instead wrote new Date(Temporal.Now.instant().toString()) (the instant() function creates a UTC timestamp rather than a plain date/time), the code would always return the correct result.

Offset Date/Time

Parsing an offset date/time such as is also potentially dangerous. When parsing this format in a language without a dedicated offset date/time type, the embedded time zone offset is often lost and will instead be treated as either UTC or local time.

For example, the JavaScript code new Date("") will discard the embedded time zone offset. Formatting the resulting Date object will then always use local time, regardless of the original offset.

Offset date/time parsing also cannot account for changes to time zone definitions, such as the Brazil example above. If an offset date/time had been used, choosing a disambiguation or even detecting the issue would not have been possible.

As mentioned above, offset date/times are not safe to use for any date/time arithmetic, because they cannot represent daylight saving or other time zone transitions. You will need to be careful to never add or subtract durations like days, weeks or months from an offset date/time value as the result will not always be correct.

Other formats

While numerous other date formats exist, most do not support embedding any time zone information, so the same caveats as for parsing RFC 3339 plain date/time values (with no offset, “Z” or time zone) apply. These formats suffer from the same ambiguities around time zone transitions and are not generally safe to use.

Formats like RFC 7231 (e.g. ) do embed time zone information, but they offer no benefit over RFC 3339/9557. RFC 3339 is easier to parse, less English-specific and generally more widely-used.

Summary and Recommendations

Serialization

Serialized timestamps should be in UTC whenever possible, using the RFC 3339 format (with a trailing “Z”).

If a local time zone is required, such as for real-world events or for doing date-time arithmetic, use the RFC 9557 format (combined offset + time zone). Ensure you are accounting for offset ambiguities when parsing, particularly for future-dated events.

JavaScript

Consider using the Temporal API if at all possible. You can find very detailed documentation on MDN. This API is carefully designed to avoid many common date/time-related bugs that may happen with other APIs. Polyfill libraries are available on NPM.

You also have the option of using the Date type, which stores UTC dates. Be careful with its parser as it has a tendency to parse non-standard strings in unexpected ways. Ensure you only pass UTC timestamps when creating Date objects. Beware of NaN dates sneaking in to calculations, and always check for that using isNaN(date.getTime()). Many getters on the Date type treat it as a local date and return values based on local time, which may not be what you expect, so be very careful when reading or writing these properties to ensure the behavior is correct.

C#

The DateTime type is very error-prone due to the way it can represent either a local plain date/time or a UTC timestamp depending on its Kind property. Make judicious use of DateTime.SpecifyKind() and DateTime.ToUniversalTime() to ensure the Kind property is always set to UTC. Be careful when serializing as C# will generally not include the “Z” suffix, which can cause other languages to treat UTC dates as local dates. Parsing DateTime values is also dangerous, as the Kind property may need to be set manually.

You can also try using the DateTimeOffset type, which will always include a UTC offset instead of falling back to a plain date/time. However, because that type does not include any time zone information, it also cannot be used for any date/time arithmetic. For date/time calculations that are not in UTC you may have to find a third-party library.

PostgreSQL

Always use the timestamptz (equivalently timestamp with time zone) type. Its name is a misnomer as it does not contain any timezone, but instead stores dates as UTC. Do not use the timestamp (equivalently timestamp without time zone) type, as it will use the server's local time.

Go

The time.Time in Go is always zoned, which can be unexpected. Consider calling .UTC() or converting it to another time zone before doing arithmetic, as it is easy to accidentally mix time zones.

Protobuf

The built-in google.protobuf.Timestamp is recommended for UTC timestamps.

Rust

std::time::SystemTime is safe to use for UTC timestamps, but it has limited support for arithmetic or serialization. Consider using a third-party library like jiff for more advanced functionality.

Java

Java has a very comprehensive set of built-in date types. java.time.Instant and java.time.ZonedDateTime are safe to use. The other types are less commonly required but are also safe to use if needed.

C

When using time_t, ensure you are using 64-bit integers as many C libraries still do not have 64-bit support enabled by default. Be careful when using struct tm as its time zone behavior is highly platform-dependent.

Swift

The Date and DateComponents types are safe to use.

Python

The datetime type is very easy to misuse as it does not consistently use time zones. Consider using a third-party library if possible.

Glossary

Time Zone

An area where all clocks are always set to the same local time (i.e. have the same UTC offset). Your current time zone is . Common time zones include America/New_York, Europe/London, Europe/Paris, UTC and Asia/Tokyo. While Europe/London is equal to UTC in winter, it follows daylight saving in summer and is thus a separate time zone from UTC.

Time Zone Offset / UTC Offset

An offset from UTC, in hours and minutes (and sometimes seconds or fractional seconds). Your current time zone offset is . The time zone UTC always has offset +00:00. Many time zones change their offset regularly, such as for daylight saving. Time zones without daylight saving will typically have the same offset, but may have changed offset in the past. For example, Asia/Tokyo does not follow daylight saving and last changed its offset in 1951.

UTC

Universal Coordinated Time, a standard time based on the prime meridian in Greenwich, London. Formerly called Greenwich Mean Time. This page intentionally ignores leap seconds, but to find out more about the precise definition of UTC, I would recommend reading up on UT1, DUT1, TAI and Terrestrial Time.

Time Zone Transition

A time zone transition is when a time zone's UTC offset changes. Every time daylight saving starts or ends, a time zone transition occurs. Time zone transitions can also happen for other reasons, such as political changes or religious events. While most changes add or subtract one hour, there are sometimes bigger changes for various reasons. When a UTC offset increases, local time is skipped; when the offset decreases, local time is repeated. Code that does not handle this correctly can suffer from transition ambiguities.

Transition Ambiguity

During a time zone transition, any repeated local timestamp becomes ambiguous, as it is not clear if it happened before or after the time zone transition. When local time is skipped, any timestamp with a value during the transition is invalid as it never occurred, making it similarly ambiguous. These two common ambiguities are called transition ambiguities.

Transition ambiguities can easily be avoided by always storing timestamps in UTC or with a time zone (i.e. in a zoned date/time), and never storing plain date/time values. Any attempt to convert a plain date/time to a zoned date/time or to a UTC timestamp will potentially suffer from transition ambiguities. See the conversion table above.

Offset Ambiguity

When a time zone definition changes (i.e. not just a time zone transition like the start or end of daylight saving, but the introduction or abolishment of daylight saving), zoned date/time values become ambiguous. See the Brazil example above for more details. Unlike transition ambiguities, offset ambiguities are somewhat unavoidable. Nonetheless, it's worth considering how to handle offset ambiguities whenever you receive or parse a zoned date/time value that could be ambiguous.

Bonus Section!

Plain Dates and Plain Times

If you don't need a full timestamp but only want to store a date, or only a time, you should use the RFC 3339 / ISO 8601 formats and . These are much easier to work with as there is no time zone to worry about, and you won't encounter potential off-by-one errors near midnight, where a standard timestamp might unexpectedly cross into the previous day.

Durations

ISO 8601 also defines a standard syntax for durations:

  • : Duration since January 1 (months, days, hours, minutes, etc.)
  • : Duration since January 1 (only seconds)
  • : Duration since January 1 (only days)
  • : Duration since you loaded this page

Durations always start with P, followed by (optional) year, month and day components. Then you can have a T before including hours, minutes and seconds. The T is needed to disambiguate months and minutes since both use an M.

One thing to be careful with when using durations is that while hours, minutes and seconds always have a consistent length; days, weeks, months and years do not. A duration of one day (P1D) is usually equal to 24 hours (PT24H), but it can also be 23 hours, 25 hours or even shorter or longer. Days of length 0 are also possible.
